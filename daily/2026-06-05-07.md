## 🔍 行业观察：拆解 Cobo Wallet — Agent Wallet 的典型产品

> 素材来源：Cobo Wallet 产品功能及使用分享（2026-06-03 线上分享会纪要）

### 产品定位

Cobo Wallet 是一个 **Agent-native 的 MPC 钱包**，核心解决的问题是：AI Agent 需要操作链上资产时，如何在"能执行"和"不能乱执行"之间建立安全边界。

### 五维拆解：谁发起/谁执行/谁付款/谁验证/谁承担风险

| 角色 | Cobo Wallet 中的对应 | 说明 |
|------|---------------------|------|
| **谁发起** | AI Agent（用户意图） | Agent 识别用户 intent，生成执行计划，发起交易请求 |
| **谁执行** | Agent + MPC 签名 | Agent 通过 CLI/API/SDK 调用发起交易，MPC 分片签名完成执行 |
| **谁付款** | 钱包中的链上资产 | Agent 操作的钱包地址中的 token/原生资产 |
| **谁验证** | 风控引擎 + 用户审批 + AI 洞察 | 三层验证：引擎规则检查、手机端人工确认、服务端 AI 风险提示 |
| **谁承担风险** | 钱包持有者（用户） | 用户是资产最终所有者，Pack 策略可限制但不能消除风险 |

### 核心技术架构

**三层结构**：
1. **后端核心服务**：钱包交易引擎 + 风控引擎 + 审批流 — 规则和约束层
2. **用户端 Agent**：Skills/MCP/CLI — 执行和工具层
3. **移动端 App**：配对确认 + 备份 — 人工验证层

**MPC 钱包架构**：
- 用户端和服务端各持有一片私钥分片
- 签名过程中**任何一方都不会在内存中生成完整私钥**
- 最终产出等同于完整私钥签名的结果
- 好处：单点泄露不等于资产泄露；坏处：签名有网络延迟，恢复依赖备份

### 两种使用模式

**Agent 模式（AI-native）**：
- 复制官网 prompt → Skills 一键安装 → 钱包创建 → 账户配对
- 未配对：Agent 可自由操作，无风控（⚠️ 适合测试，不适合生产）
- 配对后：Agent 发起交易需提交 packet，手机端人工确认
- 适合：AI Agent 自动化场景（支付、DeFi、套利）

**Developer 模式（API-driven）**：
- CLI：Skills 底层调用 CLI，创建钱包生成 profile 文件（含 API key）
- API：更底层，不需 CAW binary，但需 tss node
- SDK：对 API 的封装，Python SDK 有 AI 框架集成（Agno），TS SDK 功能较弱
- 适合：Web 服务、SaaS、固定流程任务

### Pack — 交易级行为策略约束

Pack 是 Cobo 的核心风控机制，本质是**交易级权限策略**：
- 可设置：交易次数、时间窗口、金额上限（24h/7d/30d 累计）
- 可通过 ABI 参数匹配约束特定合约调用
- ⚠️ 已知限制：数组和结构体类型 ABI 解析支持不佳；合约调用金额判断需模拟执行，功能尚不完善
- Pack 不可变 — 新需求需创建新 Pack，旧 Pack 可在手机端作废

### 分享会 Q&A 补充（原始纪要要点）

**MPC vs 多签**：
- 多签（Safe）：多把钥匙，凑够数量开锁 → 链上有多个地址
- MPC：一把钥匙拆成碎片，碎片组合签名 → 链上只有一个地址，用户体验更简洁

**Intent 识别与 AI 洞察**：
- Intent + 执行计划由 Agent 根据用户话语创建
- 人类审批时需核对：申请权限 vs 原始意图是否一致
- App 端有 AI 洞察功能：服务端大模型判断提交内容是否合理，提示风险

**X402 支付相关**：
- X402 与 Policy 引擎结合不够完善
- 可通过 message send policy 在 EIP-712 层面做限制
- 签名单认证风控方式不足，是后续迭代方向

**Web3 测试**：
- Web3 与 Web2 测试无本质区别
- 开发环境和正式环境均可测试，开发环境更友好
- Dev 环境通 → 生产环境基本也通

**技术支持**：
- Discord "cobo organic wallet" 群，24 小时值班同事答疑

**鸿蒙适配**：
- 安卓生态较散，无法兼容所有机型
- 建议使用苹果测试机（Testflight）

### 与课程内容的交叉映射

**1. Agent 章节 → Cobo 的 Intent + Policy**
- Agent 的 Planning = Cobo 的 Intent 识别
- Agent 的 Tool Use 权限分级 = Cobo 的 Policy 引擎
- Agent 的 State 外置可审计 = Cobo 的 packet + 审批记录
- **关键对齐**：Handbook 说"Agent 不是自主权本身，而是被约束的执行循环" — Cobo 的架构就是这句话的产品实现

**2. Smart Contract 章节 → Cobo 的 Pack 策略**
- 合约的 modifier/access control = Pack 的 params match + 金额限制
- 合约的 Event 日志 = Cobo 的交易记录 + AI 洞察

- **关键对齐**：Handbook 说"权限必须显式" — Pack 就是 Agent 场景下"显式权限"的技术载体

**3. Wallet 章节 → Cobo 的 MPC 架构**
- 钱包是"身份和签名入口" → MPC 让签名权分散，身份不依赖单一私钥
- 助记词/私钥的风险 → MPC 从密码学层面消除了"完整私钥泄露"的可能
- ⚠️ 但 MPC 不是万能：备份丢失 = 资产不可恢复；配对码泄露 = 签名权被劫持
- **关键对齐**：Handbook 说"钱包动作有风险阶梯" — Cobo 的"未配对自由操作" vs "配对后需确认"就是风险阶梯的实现

## 🃏 Week 1 概念卡片：AI 基础

> 来源：Handbook LLM + Context + Agent 章节 + 3天学习笔记

### LLM — 大语言模型

**核心**：LLM 是概率性文本生成器，不是知识库也不是推理引擎。它能产出合理回答，但不能保证正确。

**关键概念**：
- **Token**：文本的最小处理单位，模型按 token 预测下一个输出
- **Temperature**：控制输出随机性 — 低=确定性高，高=多样性高
- **Context Window**：一次请求能处理的最大 token 数 — 窗口大 ≠ 用得好
- **Hallucination**：模型生成看似合理但不真实的内容 — 本质是概率预测，不是故意欺骗
- **Prompt Engineering**：设计输入以引导输出 — 不是"骗模型"，而是"给正确的上下文"

**AI × Web3 注意点**：
- LLM 不能替代链上验证 — 模型说"交易成功"不等于交易真的成功
- Token 生成是概率性的 — 每次调用可能产生不同结果，合约调用参数必须确定性校验
- Prompt Injection 是 LLM 的固有风险 — 在 Agent 场景中等同于"假指令攻击"

### Context — 上下文

**核心**：Context 是模型能看到、能使用、能被影响的信息空间。关键是信息治理，不是长文本拼接。

**关键概念**：
- **Context Window**：一次请求最大上下文范围 — 关键状态直接给，长文档按需取
- **Context Engineering**：设计上下文进入模型的方式 — 选择数据源、排序、裁剪、标注来源、隔离不可信内容
- **Memory**：跨请求保留的信息（用户偏好、历史任务）— ⚠️ 隐性风险："记住上次授权"≠"这次仍应授权"
- **Knowledge Base**：可检索的外部知识库 — 必须记录来源、更新时间、适用版本、是否需人工复核

**上下文分层模型**（从高可信到低可信）：
1. 指令层：系统规则、禁止事项
2. 任务层：用户目标、会话参数
3. 事实层：链上状态、工具结果、simulation
4. 知识层：文档、标准、历史案例
5. 记忆层：用户偏好、项目配置

**AI × Web3 注意点**：
- fact 层包含正确的 chain id + 区块高度 = Chain-aware Context 的基础
- Memory 不能替代实时授权 — 过去允许 ≠ 现在仍允许
- 给模型错误信息比缺信息更危险

### Agent — 智能体

**核心**：Agent 是被约束的执行循环，不是自主决策系统。目标、工具、状态、权限和停止条件缺一不可。

**关键概念**：
- **Tool Use**：调用外部能力 — 让 Agent 从"会回答"变成"能做事"，但风险等级完全不同
- **Planning**：目标拆成步骤 — 计划是候选路线，不是授权
- **State**：当前任务状态 — 必须外置可查可审计，不能只藏在 prompt 里
- **Reflection**：检查中间结果并修正 — 不能替代外部验证，模型可能给自己的错误找理由
- **Multi-Agent**：多 Agent 分工协作 — 先问"是否真的减少复杂度"

**Agent 的安全架构**（Cobo Wallet 验证）：
- 用户提目标 → Agent 生成计划 → 系统拆只读/写入步骤 → 只读自动执行 → 写入进 policy → Simulation → 用户确认 → 执行 → 日志
- **最危险设计**：模糊目标 + 广泛工具 + 长期记忆 + 大额资产权限

**AI × Web3 注意点**：
- Agent 位在模型能力和链上执行之间
- AI 做建议和编排，钱包做授权确认，合约做可验证执行
- Reflection = 自我检查提高质量；确定性检查 = 承载风险

## 🃏 Week 1 概念卡片：Web3 基础

> 来源：Handbook Wallet + Transaction & Gas + Smart Contract 章节 + 3天学习笔记

### Wallet — 钱包

**核心**：钱包是身份和签名的入口，不是"存币的地方"。

**关键概念**：
- **地址**：公钥的衍生，链上身份标识 — 可以公开分享
- **私钥**：签名权的唯一凭证 — 泄露 = 资产归零，无法撤销
- **助记词**：私钥的人类可读备份 — 12/24 个词，泄露等同于私钥泄露
- **签名**：用私钥证明"我同意这个操作" — 不签名 = 不发生
- **Approve/Permit**：第三方代操作授权 — ⚠️ 最常见的资产损失原因

**钱包动作风险阶梯**：
1. 查看余额（只读，零风险）
2. 连接钱包（只暴露地址，低风险）
3. 签名消息（证明身份，中风险 — 可能被钓鱼）
4. Approve 授权（允许代操作，高风险 — 可被滥用）
5. 发送交易（直接转出资产，最高风险）

**MPC 钱包**（Cobo Wallet 验证）：
- 用户端和服务端各持一片私钥分片，签名过程中永远不生成完整私钥
- 好处：单点泄露 ≠ 资产泄露
- 坏处：签名有网络延迟；备份丢失 = 资产不可恢复

### Transaction & Gas — 交易与 Gas

**核心**：交易是"让链上状态发生变化的唯一方式"，Gas 是"执行成本的度量"。

**关键概念**：
- **Transaction**：签名后的链上操作请求 — 从钱包签名到确认经过：钱包→RPC→mempool→区块→共识→执行→确认→索引→浏览器
- **Gas**：计算和存储的计价单位 — gas used × gas price = 实际费用
- **Gas Price**：每单位 gas 的价格 — 越高越快被打包，越低越慢
- **Gas Limit**：发送者愿意支付的最大 gas — 不够 = revert + 扣费
- **Nonce**：地址的交易计数器 — 防止重放攻击，保证交易顺序
- **Confirmation**：交易被后续区块确认 — 确认数越多越安全

**交易生命周期**：
1. 构造交易（to/value/data/gas limit/nonce/gas price）
2. 钱包签名
3. 广播到 RPC 节点
4. 进入 mempool
5. 验证者打包进区块
6. 共识确认
7. EVM 执行（成功=更新状态+emit event；失败=revert+扣 gas）
8. 区块浏览器索引

### Smart Contract — 智能合约

**核心**：合约是部署在链上的程序，价值来自可验证执行，不是"代码看起来很聪明"。

**关键概念**：
- **Solidity**：EVM 最常见合约语言 — 关键在 storage/msg.sender/modifier/event/external call/revert/权限控制
- **EVM**：合约执行环境 — 解释了为什么要 gas、为什么 storage 贵、为什么外部调用有风险
- **ABI**：合约的机器可读接口 — 告诉"能调用什么"，**不保证调用是否安全**
- **Event**：合约向外部系统的可索引日志 — 前端历史记录通常来自 event 索引，不是直接读 storage
- **Upgrade**：合约升级是安全/治理/迭代的权衡 — 判断升级风险四问：权限在谁？用户能否提前看到？能改什么？密钥泄漏最坏结果？

**常见错误**：view vs 写交易混淆、decimals 未处理、只测成功路径、owner 当可信、忽略 event 设计

**AI × Web3 定位**：AI 做建议和编排，钱包做授权确认，合约做可验证执行，监控系统记录结果。

## 🛠️ WCB API 核查经验与踩坑记录

> 这部分记录了 06-05~06-07 期间对 WCB（Web3 Career Build）Agent API 的完整核查过程，包括踩坑和解决方案

### 1. API Endpoint 的曲折发现

**问题**：初始调用使用 `/api/agent` 路径，返回 HTML/404 而非 JSON

**排查过程**：
1. 先尝试 `https://web3career.build/api/agent` → 返回 HTML 页面（404）
2. 尝试 `https://agent-api.wcb.wtf` → 域名已失效（DNS 不解析）
3. 通过 `https://web3career.build/llms.txt` 找到 API 文档入口
4. 最终确认正确端点为 **`/api/agent/call`**

**教训**：
- 旧文档/教程中的 API 地址可能已失效，优先从 `llms.txt` 获取最新信息
- API 返回 HTML 而非 JSON 通常意味着路径错误，不是服务挂了
- `agent-api.wcb.wtf` 域名已废弃（截至 2026 年 5 月），不要再用

### 2. 认证方式踩坑

**问题**：最初用 `Authorization: Bearer <key>` 发送请求，返回认证失败

**解决**：
- WCB Agent API 使用 **`X-Secret-Api-Key`** header，不是 `Authorization: Bearer`
- API Key 存储在 `~/.wcb.env`，变量名 `WCB_AGENT_SECRET_API_KEY`
- 文件权限应设为 600

**教训**：
- 不同 API 的认证方式差异很大，不要假设都是 Bearer Token

## 🌐 WSL 网络问题与解决方案

### 问题描述

**现象**：
- `curl -sk` 可以直接访问 Cobo/Cobo Dev API（返回 JSON 响应）
- CAW CLI（Go binary）调用同一个 API 超时
- DNS 解析结果为 `198.18.x.x`（Cloudflare WARP 保留地址段）

**根因分析**：
- WSL + Mihomo Party（Windows 上运行的代理客户端）TUN 模式劫持了 DNS
- Go 的 `net/http` 使用系统 DNS 解析器，与 curl 可能走不同的解析路径
- WSL 中 DNS 将外部域名解析到 WARP 保留 IP，Go binary 直连这些 IP 超时

### 解决方案

**方案 1 — 设置 HTTPS_PROXY 环境变量**（✅ 推荐且已验证）：
```bash
export HTTPS_PROXY=http://172.18.240.1:7890
```
- `172.18.240.1` 是 WSL 中看到的 Windows host IP
- `7890` 是 Mihomo Party 的代理端口
- 对 CLI/API 调用均有效

**方案 2 — 修改 WSL DNS 配置**（未验证）：
```bash
# /etc/resolv.conf
nameserver 8.8.8.8
```
- 风险：可能影响 WSL 内部域名解析

**方案 3 — 临时关闭 Mihomo TUN 模式**：
- 在 Windows 端关闭 TUN → WSL DNS 恢复正常 → 操作完再开
- 适合偶尔需要 CLI 操作的场景

### 通用判断模式

**"环境依赖型踩坑"的特征**：
1. curl/browser 正常，但特定语言 runtime 超时
2. DNS 解析到异常 IP（198.18.x.x / 100.64.x.x 等 CGNAT 范围）
3. 所有依赖外部 API 的 CLI 操作全部阻塞
4. 同一命令在其他环境（macOS / 原生 Linux）正常

**排查步骤**：
1. 先 `curl -sk` 验证 API 本身是否可达
2. `nslookup` / `dig` 检查 DNS 解析结果
3. 如果解析异常，确认是否有 TUN/VPN 模式运行
4. 设置 `HTTPS_PROXY` 并重试
