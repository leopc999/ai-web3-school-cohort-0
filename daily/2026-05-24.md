## 📖 Vibe Coding — 氛围编程

> 来源：https://aiweb3.school/zh/handbook/ai/vibe-coding/

### 核心定位

Vibe Coding 不是"把需求丢给 AI 然后等代码出现"。更准确地说，它是一种**人和 AI Coding Agent 共同迭代软件的工作方式**：人负责方向、约束和验收，Agent 负责生成、修改、搜索和执行一部分工程动作。

### 为什么要学这个

AI Coding Agent 已经能读代码、改文件、跑测试、解释错误、生成 PR。速度变快之后，真正的问题变成：

- 你能不能**清楚描述任务**？
- 你能不能**审查结果**？
- 你能不能**控制改动范围**？
- 你能不能**验证没有引入新 bug**？

Vibe Coding 最容易被误解成"凭感觉写代码"。实际可用的做法正好相反：**你要更清楚地管理 repo、任务、上下文、测试和提交边界。**

> AI 能帮你写更多代码，但不能替你承担工程判断。

### 第一性原理

AI Coding 的核心不是自动生成代码，而是**把工程反馈循环压短**。

过去：自己搜索文件 → 理解模块 → 改代码 → 跑测试 → 看错误 → 再修改。现在 Agent 可以并行承担很多步骤。但如果反馈循环里没有测试、审查和版本控制，速度只会放大混乱。

三条原则：
1. **任务要小** — 越具体、越有边界，Agent 越容易产出可审查结果
2. **上下文要准** — 让 Agent 看对文件、设计约束和错误输出，比写长篇需求更重要
3. **验证要硬** — 运行测试、类型检查、构建、截图或日志，比"看起来对"可靠

### 知识节点

#### 1. Vibe Coding（难度：初级）

人和 AI Coding Agent 的分工：
- **人负责**：目标、边界和验收
- **Agent 负责**：搜索、生成、修改和执行

Vibe Coding 是一种快速和 AI 共同探索代码的方式。先描述目标 → Agent 生成方案或 patch → 运行、检查、追问、迭代收敛。

适合场景：
- 搭原型
- 修小 bug
- 补测试
- 写脚本
- 重构局部模块
- 解释陌生代码

**不适合**无边界地"重写整个项目"——如果任务范围太大，Agent 很容易改到不该改的地方，或引入看似合理但不符合项目约束的抽象。

#### 2. Claude Code / Codex CLI（难度：初级）

重点不是背命令，而是学会**把 AI Agent 安全地接入本地 repo、终端和测试流程**。

这类工具的关键价值不是"聊天"，而是能在 repo 里行动。正因为它能行动，你需要明确：

- 哪些文件可以改
- 哪些命令可以跑
- 是否允许安装依赖
- 是否允许访问网络
- 什么时候必须停下来让人确认

相关工具：
- Claude Code Docs：了解 Claude Code 的本地开发工作流
- OpenAI Codex CLI Help：了解 Codex CLI 的基础使用方式

#### 3. Model / API Config（难度：中级）

这一层要处理模型选择、API key、工具权限、上下文、成本和日志，不只是"能不能调用成功"。

常见问题：
- 本地和 CI 用的模型不一致
- API key 泄漏到日志或提交里
- 上下文太长导致成本失控
- Agent 使用了不合适的工具权限
- 输出风格和项目规范不一致

好的配置应该能被团队复用，而不是每个人在本机随手调。

**OpenCLI** 值得关注：把网站、浏览器会话、Electron 应用和本地二进制工具统一成可被命令行调用的接口，让 AI Agent 可以通过更稳定的命令去发现、学习和执行工具。它还可以复用本地浏览器登录态，并把 gh、docker 等本地 CLI 暴露到同一个工具入口里。

这类工具的价值不在于"又多一个 AI 编程产品"，而在于把 Agent 可调用的外部能力变得更清楚：有哪些命令、需要什么权限、输出格式是什么、失败时怎么诊断。

#### 4. GitHub / gh（难度：中级）

你需要把 AI 生成的改动放回版本控制、issue、PR 和 review 流程里，而不是只看一次聊天输出。

实用原则：**让 Agent 多做局部 patch，少做不可追踪的大改动。**

每次改动后至少看：
- `git diff`
- 修改文件列表
- 测试结果
- 是否包含不该提交的密钥、日志、构建产物

#### 5. CLI / Script（难度：中级）

这一层开始把 Agent 输出变成真实命令和脚本，所以要特别关注**读写范围、dry run 和外部副作用**。

很多开发任务不需要完整应用界面，先写 CLI 或脚本更快。Agent 很适合帮你生成一次性脚本、数据迁移脚本、检查脚本和批量修改脚本。

脚本的两个边界：
1. 读写文件前要确认范围
2. 会修改外部状态的脚本要先 dry run

如果脚本会删文件、发请求、改数据库、提交交易或调用生产 API，就不能只靠 Agent 判断。

#### 6. Repo Workflow（难度：高级）

你要把 AI Coding 接进完整工程流程，并能判断**什么时候应该让 Agent 继续，什么时候必须由人停下来审查**。

Repo Workflow 是把 AI Coding 放进正常工程流程：issue → branch → commit → test → review → merge → release。

不要让 AI 绕过这些流程。更好的方式是让它参与这些流程：
- 从 issue 提炼任务边界
- 搜索相关文件
- 生成最小 patch
- 跑测试并解释失败
- 补充 changelog 或文档
- 写 PR summary 和验证说明

> AI Coding 的质量，最终还是要落到 repo workflow 里。

### 在 AI × Web3 中的位置

AI × Web3 项目通常同时有前端、合约、脚本、索引器、Agent 后端和文档。Vibe Coding 可以显著加快探索速度，尤其适合 hackathon 和早期原型。

但**链上相关代码的风险更高**。合约、签名、权限、支付、迁移脚本不能只靠 Agent 生成后直接上线。AI Coding 可以帮你写测试、解释 ABI、生成脚本，但高风险动作必须经过审查、模拟和多方确认。

### 最小实践

选择一个小功能，让 AI Coding Agent 完成一轮完整工程闭环：

1. 写清楚任务边界和不能改的文件
2. 让 Agent 搜索相关代码并给出计划
3. 让 Agent 做最小 patch
4. 运行测试或构建
5. 查看 git diff，手动审查结果
6. 要求 Agent 写一段 PR summary 和验证说明

完成后记录：哪些信息给少了，哪些测试缺失，哪些改动需要人类判断。

### 挑战

在自己的电脑上安装并配置至少一个 Vibe Coding 工具（例如 Claude Code、Codex CLI 或 OpenCLI），并确认它能在一个测试 repo 中正常使用。

完成标准：
- 能启动工具并读取当前项目
- 已配置必要的模型、API key、浏览器桥接或本地工具权限
- 能让工具完成一个只读任务（解释目录结构、搜索相关文件、总结某段代码）
- 能让工具完成一个低风险小改动（补一段注释、生成一个脚本、修改一处测试）
- 保留验证记录：工具版本、配置方式、执行命令、关键输出或截图

## 🔧 Vibe Coding 实践记录：用 Hermes Agent 搭建学习工作流

> 这是 Week 1 实践交付之一：记录使用 Hermes Agent 作为 Vibe Coding 工具的真实过程

### 背景

Hermes Agent 是一个开源 AI Agent 框架（by Nous Research），支持 Telegram、Discord、Slack 等多平台，能通过工具调用在本地终端执行命令、读写文件、搜索网页、管理定时任务等。我在 AI × Web3 School 共学期间，将 Hermes Agent 作为主要的 Vibe Coding 工具来辅助学习。

### 实践一：Telegram DM Topic Session 持久会话配置

#### 问题

默认情况下，Telegram 私聊中的 Hermes Agent 每条消息都创建一个新 session，导致：
- 学习上下文在每条消息后断裂
- 前一条消息中讨论的 WCB API 信息、项目结构等在下一条消息中丢失
- 必须频繁重复信息（如 programId、API 调用方式等）

#### 探索过程

1. **提出需求**：希望学习相关的消息归入同一个持久会话，不想每次切换
2. **发现方案**：Hermes 支持 Telegram DM Topic Sessions — 每个私聊 Topic 映射到一个独立的持久会话
3. **确认可行性**：
   - 起初不确定 DM 是否支持 Topic（Telegram 原生 Topics 是群聊功能）
   - 通过查阅 Hermes 源码和文档，确认 Telegram Bot API 9.4+ 支持 `createForumTopic` 在私聊中使用
   - Hermes 在 DM 中复用了这个能力，每个 Topic = 一个独立 session
4. **配置步骤**：
   - 在 Telegram 客户端中开启私聊 Topics（点击 Bot 名称 → 设置 → Topics 开关）
   - 发送 `/topic` 命令激活多会话模式
   - 通过 "All Messages" 创建新 Topic（如 "AI × Web3 School"）
   - 通过右上角 ⋮ → Edit Thread 重命名 Topic

5. **Session 绑定问题**：
   - 遇到 "That session is already linked to another Telegram topic" 错误
   - 原因：新 Topic 创建时，之前的 session 还绑定在旧 Topic 上
   - 解决：在新 Topic 中发 `/new` 开启全新会话，自动绑定到当前 Topic
   - 通过 `/topic <session-id>` 也可以恢复历史会话

#### 配置结果

| Topic 名称 | 用途 | Session 持续性 |
|---|---|---|
| AI × Web3 School | 学习讨论、任务提交 | 持久（跨天自动接续） |
| General | 日常闲聊 | 持久 |

#### Vibe Coding 对照

- **人负责方向**：我决定按用途划分 Topic，设定哪些消息归属学习
- **Agent 负责执行**：Hermes 自动处理 session 绑定、Topic 创建和消息路由
- **验证要硬**：每次操作后确认 session 状态（`/topic`、`/status`），确保绑定正确
- **任务要小**：不试图一次搞定所有配置，先创建 Topic → 测试绑定 → 再调优

### 实践二：Telegram Reaction 功能开启与调试

#### 问题

Hermes 的 Reaction 功能默认关闭。开启后，Bot 会在用户消息上添加 emoji 反应来表示处理状态，提供视觉反馈。

#### 功能说明

- 👀 — Bot 开始处理你的消息时
- ✅ — 响应成功发送后
- ❌ — 处理出错时

Telegram 的 Bot API 是**替换式**的（不是叠加的），所以 👀 变成 ✅ 时是直接看到切换，不会同时出现两个。

#### 配置过程

1. **开启配置**：在 `config.yaml` 中设置 `telegram.reactions: true`
2. **重启 gateway**：配置变更需要重启 `hermes-gateway` 服务
3. **遇到的问题**：
   - 首次重启时 gateway 正在 draining（等待活跃 agent 会话结束），重启命令超时
   - 改用 `systemctl --user restart hermes-gateway` 强制重启
   - 重启后需要确认 gateway 状态为 `active`
   - Reaction 未立即生效，需要发 `/restart` 让 gateway 重新加载配置
4. **最终确认**：发送消息后观察到 👀 → ✅ 的 emoji 切换，功能生效

#### 社区观点调研

关于 Telegram Bot 使用 Reaction 作为状态反馈，社区有两种看法：

**正面**：
- 提供即时视觉反馈，用户不用等待文字回复就知道 Bot 在处理
- 减少焦虑感——看到 👀 就知道"收到了"
- 不干扰聊天流，比发"处理中..."的文字消息更优雅

**负面**：
- 部分用户觉得消息上突然出现 emoji 很突兀
- 在高频对话中，Reaction 的频繁切换可能分散注意力
- 不是所有用户都注意到 Reaction 的变化（尤其是视觉不敏感的用户）

#### Vibe Coding 对照

- **上下文要准**：Reaction 是轻量级反馈，不替代文字响应，而是补充
- **验证要硬**：通过实际发消息测试确认 Reaction 生效，而非假设配置正确
- **工具权限边界**：Reaction 功能是 Telegram Bot 的能力之一，Hermes 选择默认关闭，让用户主动开启——这和 Vibe Coding 的"什么时候必须停下来让人确认"原则一致

### 实践三：用 Hermes Agent 驱动学习流程

#### 整体工作流

```
用户指定学习目标 → Agent 抓取章节内容 → 解析写入笔记 → 
更新学习计划 → Git commit + push → 查看任务列表 → 提交 PoW
```

#### 具体交互记录

1. **章节学习**：
   - 用户说"今天学 Agent 章节"
   - Agent 用 `terminal` 调用 `curl` 抓取 `aiweb3.school` 页面
   - 首次超时（WSL 网络问题），改用 `-sk` 跳过 SSL 验证成功下载
   - 解析 HTML 提取内容，写入 `daily/YYYY-MM-DD.md`

2. **WCB API 调用**：
   - 用 `tasks.listForLearner` 查询可提交任务
   - 遇到多个问题：
     - 端点错误：`/api/agent` → 404，正确端点是 `/api/agent/call`
     - 参数缺失：只传 `programId` → BAD_REQUEST，必须同时传 `trackId`
     - 认证方式：`Authorization: Bearer` 无效，必须用 `X-Secret-Api-Key` header
     - 大响应输出为空：改用 `-o` 写文件再读文件解析
     - JSON 控制字符：需 `json.loads(raw, strict=False)` 才能解析
   - 最终成功获取 41 个任务、700 总积分

3. **Git 工作流**：
   - 每次笔记写入和学习计划更新后，`git add + commit + push`
   - 使用描述性 commit message（如 "Week1: 完成 Agent(AI)+Smart Contract(Web3) 章节学习笔记"）

4. **Session 连续性**：
   - 在 Topic 模式开启前，跨 session 通过 `memory` 和 `session_search` 恢复上下文
   - 开启后，同一 Topic 内自动延续会话，不再断裂

#### Vibe Coding 对照

- **任务要小**：一次一个章节学习，而非"一次搞定所有"
- **人负责方向和验收**：我指定学什么、查什么任务、提交什么
- **Agent 负责搜索和生成**：抓取网页、解析内容、写入笔记、调用 API
- **验证要硬**：
  - 每次都 `git diff` + push
  - API 结果写文件再解析，不信任 pipe 输出
  - 网络超时自动重试
- **边界意识**：
  - Agent 不主动修改关键配置（如 API key 存储方式）
  - 高风险操作（如 `systemctl restart`）需要用户批准
  - 破坏性命令有 approval 机制把关

### 实践总结

#### 成功模式

1. **小任务 + 明确目标 = 高成功率**：一次只做一件事（学一个章节、调一个 API、开一个配置）
2. **人-Agent 分工明确**：人定方向、Agent 执行细节，效率最高
3. **验证驱动**：每步验证（git status、API 响应、配置生效），避免错误累积
4. **Memory + Session Search 弥补上下文断裂**：即使 session 断了，关键信息还在

#### 失败/踩坑记录

| 问题 | 原因 | 解决方式 |
|---|---|---|
| `aiweb3.school` 页面超时 | WSL 网络对某些 HTTPS 连接不稳定 | 用 `curl -sk` 跳过 SSL 验证 |
| WCB API `/api/agent` 404 | 端点错误 | 正确端点 `/api/agent/call` |
| `tasks.listForLearner` BAD_REQUEST | 缺少 `trackId` 参数 | 必须同时传 `programId` + `trackId` |
| API 认证失败 | 用了 `Authorization: Bearer` | 必须用 `X-Secret-Api-Key` header |
| `execute_code` 中 `terminal()` 的 `-o` 写文件为空 | Sandbox 环境路径不存在 | 改用直接 `terminal` tool 执行 curl |
| Gateway restart 超时 | 有活跃 agent 会话，draining 阻塞 | 用 `systemctl` 强制重启 + `/restart` |
| Session 绑定冲突 | 旧 session 已绑定到另一个 Topic | 在新 Topic 发 `/new` 创建新 session |
| Topic 开关找不到 | Telegram 界面不直观 | Bot 发截图指引，或在 Bot 设置中找 |

#### Vibe Coding 的"反直觉"点

1. **Vibe Coding 不凭感觉** — 越是"氛围"，越需要明确的边界
2. **速度加快后，审查更重要** — 不是省掉审查，而是审查频率要跟上速度
3. **Agent 不是替代判断，而是放大判断** — 好的判断被放大为好的代码，草率的判断被放大为草率的代码

#### Web3 场景的特殊风险

合约、签名、支付相关代码 — Agent 可以辅助生成，但必须：
- 在测试网先验证
- 经过多方 review
- 模拟边界情况
- 不能"看起来对"就上线

## 💡 个人思考

### 与 Hermes Agent 的对照

自己正在使用的 Hermes Agent 就是 Vibe Coding 的一种实践：
- **人负责方向和验收** — 我指定学习目标和提交任务，Agent 执行具体步骤
- **Agent 负责搜索和生成** — 抓取网页、解析内容、写入笔记、调用 API
- **验证要硬** — 每次都 git diff + push，API 结果写文件再解析
- **任务要小** — 一次一个章节学习，而非"一次搞定所有"

### 实践体会

这次 Vibe Coding 实践最大的体会是：**配置和调试本身就是 Vibe Coding**。

很多人以为 Vibe Coding 就是"写代码"，但实际使用 AI Agent 的过程中，大量时间花在：
- 配置工具（Topic Session、Reaction、Gateway 服务）
- 调试集成问题（API 端点、认证方式、网络超时）
- 设计工作流（学习→笔记→提交的闭环）

这些同样是"人和 Agent 共同迭代"的过程——人提需求和验收标准，Agent 尝试方案，人审查结果，Agent 修正，迭代收敛。
