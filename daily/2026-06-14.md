## 二、知识框架总结

经过一个月的学习，建立了以下认知框架：

### AI 层（推理能力）

```
LLM（概率模型）→ Context（信息空间）→ Agent（被约束的执行循环）
    ↕                    ↕                      ↕
Embedding / Token    Context Engineering     Tool Use / Planning
    ↕                    ↕                      ↕
Hallucination        Memory / Knowledge Base  Reflection / Multi-Agent
```

**核心教训**：模型输出是候选结果不是事实本身；Agent 的核心不是自主权而是被约束的执行循环；工具比回答更危险。

### Web3 层（可验证执行）

```
Wallet（身份入口）→ Transaction（状态变更）→ Smart Contract（规则执行）
    ↕                      ↕                         ↕
EOA / AA / 多签        Gas / EIP-1559            ABI / Event / Upgrade
    ↕                      ↕                         ↕
Session Key / Policy   Simulation / Guard        DeFi / Oracle / Indexing
```

**核心教训**：钱包不只是签名按钮而是权限系统；链上操作不可逆所以验证必须前置；Agent 不应直接控制主资产。

### Bridge 层（AI × Web3 交汇）

```
Chain-aware Context（让 AI 看到正确的链上状态）
    → Web3 Tool Use（把链上操作变成可约束的工具）
    → Agent Workflow（多步执行的安全流程设计）
    → Agent Wallet（权限的可编程表达）
    → Machine Payment（自动化的资金流）
    → Settlement & Escrow（去信任的结算协议）
```

**核心教训**：所有进入模型的内容都可能是攻击面，所有离开模型的动作都必须被约束。AI 负责推理，Web3 负责状态和结算，Context 决定模型看到的是幻想还是事实。

## 三、最深刻的三个认知转变

### 1. 从"AI 能做什么"到"AI 做的事如何被约束"

学习前：关注 AI Agent 的能力上限——能不能自动交易、能不能自主发现服务。
学习后：关注 AI Agent 的安全边界——权限如何表达、如何限制、如何撤销、如何审计。

> Agent 不是自主权本身，而是被约束的执行循环。目标、工具、状态、权限和停止条件缺一不可。

### 2. 从"钱包是余额"到"钱包是权限系统"

学习前：钱包 = 地址 + 余额 + 发送/接收。
学习后：钱包 = 权限表达系统（谁能操作、能操作什么、什么时候失效、超出边界怎么办）。AA、Session Key、Policy、Guard、Simulation 都是钱包作为权限系统的不同层次。

> 控制权不能交给一个概率系统。Agent 只能拿到可验证、可限制、可撤销的行动空间。

### 3. 从"AI + Web3"到"推理层 × 结算层的可信交汇"

学习前：AI × Web3 = AI 帮 Web3 写代码 + Web3 给 AI 提供数据。
学习后：AI × Web3 的真正价值在于推理能力（AI）与可验证执行（Web3）的可信交汇——AI 生成候选方案，Web3 提供确定性约束和可审计结算。

> LLM 越靠近执行层，系统越要把自然语言输出变成可验证对象。

## 四、项目拆解能力提升

通过 Cobo Wallet 的完整拆解，形成了可复用的项目分析方法：

**五维拆解框架**：谁发起 / 谁执行 / 谁付款 / 谁验证 / 谁承担风险

以 Cobo CAW 为例：
- **谁发起**：AI Agent（识别用户 intent，生成执行计划）
- **谁执行**：Agent + MPC 签名（分片签名完成执行）
- **谁付款**：钱包中的链上资产
- **谁验证**：风控引擎 + 用户审批 + AI 洞察（三层验证）
- **谁承担风险**：钱包持有者（用户），Pack 策略可限制但不能消除风险

这套框架后来成为理解 Agentic Commerce 全链路的标准工具，也帮助了赛道方向的判断。

## 六、遗憾与反思

### 黑客松未能参加

由于时间原因，最终遗憾没有参加黑客松的 Demo 环节。回顾来看：

- **已完成**：赛道选择（Cobo Agentic Economy）、项目方向确定（Budget Guardian: 自然语言→CAW Pact Policy）、技术预研（CAW CLI/API/SDK 全链路跑通）、2 次测试网转账成功
- **未完成**：核心功能 Demo（自然语言解析→Policy 生成→Pact 提交的完整闭环）、演示视频、项目 README 和最终提交

最大的遗憾不是"没做出 Demo"，而是**实操阶段的时间分配不够高效**——WSL 网络问题和合约调用调试消耗了太多时间，导致核心功能开发被推迟到了无法完成的时间点。

### 其他反思

1. **"补盲"模式容易变成"刷章"**：05-30 一天补完 15+ 章节虽然打通了阅读闭环，但深度理解不够。应该更早开始配对学习，而不是集中突击。
2. **实操起步太晚**：CAW 的实操从 06-04 才开始，距离 Hackathon Build Period 结束只有 8 天。如果从 Week 2 就开始动手，会有更多时间调试和开发。
3. **踩坑记录的价值被低估**：WSL 代理问题、CLI 参数缺失、Pact 计数逻辑这些踩坑看起来是"环境问题"，但实际上是真实开发中常见的阻碍——如果更早把这些坑踩完，后面会更顺畅。

## 七、带走的三个问题

1. **合约调用为什么失败？** transfer 正常但 contract_call 连续失败，根因可能是 ABI 解析、参数编码或 Dev 环境的已知限制——这个问题值得继续追查。
2. **ERC-8004 / ERC-8183 的实际落地差异**：Agent 间去信任工作协议的标准还在草案阶段，实际工程中怎么用？
3. **去中心化 AI 的工程边界**：链上协调层 vs 执行层的分界线在哪里？当推理和执行都需要可验证时，什么放链上什么放链下？

## 八、给下一期 Cohort 的建议

1. **实操和阅读并行**，不要先读完再做——Week 1 就开始装钱包、跑测试网
2. **踩坑要提前踩**，环境配置、网络问题、CLI 参数都是时间黑洞
3. **选赛道要早、换赛道要快**，方向犹豫比做错方向更浪费时间
4. **每个概念都用"五维框架"检验**：谁发起/谁执行/谁付款/谁验证/谁承担风险——这个框架比任何单章知识点都更有用
